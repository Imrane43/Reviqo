# Rapport d'audit — secrets, configuration et intégrations

Audit du code réel (aucune valeur secrète n'est reproduite ici). Objectif : vérifier la
manipulation des secrets et corriger les intégrations (OpenAI, e-mail, Google, vidéo).

## 1. Secrets (priorité 1)

| Vérification | Résultat |
|---|---|
| Clé API importée dans le frontend | **Aucune** — `public/` ne contient ni `process.env`, ni clé. |
| Appel direct OpenAI/Resend/Google/Stripe depuis le navigateur | **Aucun** — tout passe par le backend. |
| Secrets dans les logs | Les journaux ne contiennent jamais de corps de message ni de clé (`[mailer]` ne logue que le fournisseur et l'erreur). |
| Secrets dans Git | `.env` n'est pas versionné ; `.env.example` ne contient que des valeurs vides/factices. |
| Clé renvoyée au client | Le Coach renvoie seulement `coachKeySet: true/false` ; l'export de données exclut tout secret. |

Ces points sont désormais **vérifiés automatiquement** par la suite de tests (analyse statique de
`public/`).

## 2. Bug réel corrigé — OpenAI (priorité 3)

- `content.js` postait les arguments bruts sur `LLM_API_URL`, sans `/chat/completions`, et pouvait
  utiliser une **page de gestion** (`platform.openai.com/...`) comme endpoint.
- Correction : client `src/openai.js` (API *chat completions*), base normalisée
  (`https://api.openai.com` → `https://api.openai.com/v1`), **rejet** des URL de gestion, alias
  `OPENAI_API_KEY`/`OPENAI_BASE_URL`, modèle `LLM_MODEL`.
- Erreurs explicites renvoyées à l'interface : `KEY_MISSING`, `INVALID_KEY`, `QUOTA`, `BAD_MODEL`,
  `UNAVAILABLE`, `BAD_RESPONSE`, `PROVIDER_ERROR`.

## 3. Configuration centralisée (priorité 2)

Nouveau module `src/config.js` : `config.app`, `config.auth`, `config.ai`, `config.email`,
`config.google`, `config.video`, `config.stripe`, `config.ads` + `getAppOrigin(req)` +
`validateConfig()` appelée au démarrage (`src/server.js`). En production, une `JWT_SECRET`
manquante bloque le démarrage ; les autres problèmes sont signalés en avertissement.

## 4. APP_ORIGIN (priorité 6)

`getAppOrigin()` est l'unique source d'URL (vérification d'e-mail, OAuth, redirections, liens).
Si `APP_ORIGIN` est vide, l'origine est déduite des en-têtes (`x-forwarded-proto`/`host`), sinon
`http://localhost:PORT`.

## 5. E-mail / Resend (priorité 5)

- Lecture `.env` durcie (`src/env.js`) : guillemets, préfixe `export`, retours à la ligne parasites
  recollés, clés assainies (aucun espace/saut de ligne) — cause classique d'un `RESEND_API_KEY`
  invalide.
- Avertissement (sans afficher la valeur) si la clé ne ressemble pas à une clé Resend (`re_`) ou si
  `MAIL_FROM_EMAIL` est invalide.
- Nouvelles routes : `POST /api/auth/send-verification` et
  `GET /api/auth/verify-email?email=&token=`. Le lien est **aléatoire, haché en base, temporaire
  (`VERIFY_LINK_TTL_MINUTES`, 30 min par défaut) et à usage unique**.
- On ne considère jamais un e-mail comme envoyé : l'issue vient de la **réponse réelle** du
  fournisseur (`{ delivered, provider, reason }`).

## 6. Google Sign-In (priorité 7)

Callback construit via `getAppOrigin()` (**identique** au serveur et à la console Google) et
**protection CSRF `state`** : cookie httpOnly aléatoire, vérifié au retour. Cas gérés : refus,
`state` invalide, erreur serveur. Aucun doublon (l'utilisateur est retrouvé par `google_id` ou par
e-mail canonique).

## 7. Vidéo IA (priorité 8)

`src/videoai.js` : file de jobs avec états `pending` / `processing` / `completed` / `failed`,
`POST /api/ai/video`, `GET /api/ai/video/:id` (polling), `GET /api/ai/videos` (historique), quotas
`VIDEO_DAILY_LIMIT` et cache `VIDEO_CACHE_TTL_HOURS`.

**Honnêteté** : aucun fournisseur de génération vidéo n'est identifiable dans le projet ; il n'est
donc **pas inventé**. Sans `VIDEO_AI_API_KEY` + `VIDEO_AI_API_URL`, le job est marqué `failed` avec un
message explicite et l'utilisateur est orienté vers la recherche YouTube (réelle) ou la vidéo
générée depuis son cours. Si un fournisseur compatible OpenAI est configuré, l'adaptateur générique
(`{base}/videos`, `VIDEO_AI_MODEL`) est utilisé — à ajuster selon le fournisseur retenu.

## 8. Programmes & cours (priorités 9 à 12)

- Filtrage **strict** par profil : `courses.curriculum_id` + spécialités + matière. Un élève de 3ᵉ ne
  reçoit jamais un cours de Première.
- `GET /api/courses` → `getPersonalizedCourses(user)`.
- `POST /api/ai/courses` → génération structurée (title, objective, prerequisites, sections,
  examples, method, commonMistakes, exercise, correction, quiz, summary, flashcards) adaptée au
  niveau exact.
- **Anti-doublon** : empreinte (`fingerprint`) unique en base + similarité de titre ≥ 0,8 ; jusqu'à
  3 variantes demandées à l'IA avant de refuser (`409 DUPLICATE`).
- Sans clé IA, la génération renvoie **`503 AI_NOT_CONFIGURED`** : jamais de faux cours.

## 9. Rappels

- Ne jamais utiliser `LLM_API_URL` pour une page de gestion : fournir une **base d'API**.
- Vérifier les noms de variables nécessaires (jamais leurs valeurs) : voir `docs/EXTERNAL-SERVICES.md`.
